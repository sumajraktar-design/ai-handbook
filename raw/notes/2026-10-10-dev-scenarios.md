# 真实开发场景中的 AI 问题（2026-10-10 对话整理）

学习 AI 概念之后，结合实际开发提出的 9 个问题和结论。这是原始笔记，尚未编译进 wiki 概念页。

## 1. AI 是概率性的，生产要求 100%，什么场景适合交给 AI？

判断标准：出错代价 × 能否快速验证。

- 代价低、易验证（写初稿、解释报错）→ 放手用
- 代价高、易验证（业务代码、迁移 SQL）→ AI 生成，必须经过测试和审查
- 代价高、难验证（生产删除、转账、权限）→ AI 只辅助，人来决策
- 规则明确、要求绝对精确（金额计算、权限判断、多环境同步的 diff）→ 交给确定性代码，AI 帮忙写这段代码

原则：确定的事交给代码，模糊的事交给 AI，重要的事留给人。可靠性来自多层检查叠加，不来自模型本身。

## 2. Claude App、ChatGPT App 是 Agent 吗？

Claude、GPT 是模型；App 是产品，配上了工具和循环，执行任务时以 Agent 方式工作。可以通过连接器（MCP）读写外部服务、操作浏览器和电脑；Claude Code 能改代码、跑测试、开 PR。写入类操作默认需要用户确认。

## 3. AI 写代码太快，人看不过来，多轮 AI 自查又不划算

原因：瓶颈从"写"转移到"验证"；同一模型自查盲点重合，收益急剧递减。

做法：
- 不生成超过能验证的量：小任务、小 PR
- 人从"审查员"变成"出题人"：先定验收标准和测试
- 机器能查的不用人和 Token 查：类型检查、Lint、测试、CI
- 按风险分级审查
- AI 审查只做一次，换角度、给清单
- 上线后兜底：功能开关、灰度、回滚

## 4. 产品用 AI 写文档偏一点，开发用 AI 写代码又偏一点，最后靠测试兜底

原因："传话游戏"效应。AI 遇到没说清的地方不提问，用最常见的写法自动补全，偏差逐层累积。

做法：产品亲手写验收标准作为锚点；要求 AI 列"待确认问题"而不是自己假设；测试提前到需求阶段；交付时逐条对照验收标准；小步迭代。（对应 ATDD / BDD）

## 5. AI 的能力是"取行业均值"吗？

默认输出接近最常见的写法，但模型学到的是整个分布：上下文和标准决定它从哪一段取样；后训练让它偏向更好的回答；在可验证任务上用强化学习可能超越训练数据。能力分布参差不齐。想要高于平均的输出，就要提供高于平均的输入。

## 6. 模型的创造力从哪来？

把学到的抽象模式在新场景里重新组合，加上具体约束带来的定制感，以及"写、看、改"的迭代。新意主要在组合方式和贴合度。新颖不等于正确。

## 7. 企业知识库用的是哪里的知识？

事实来自企业自己的资料，模型负责理解和组织语言。送进上下文的方式：RAG 检索、Agent 通过 MCP 调用企业系统的搜索、资料少时直接放进上下文。

## 8. Skills 和 Rules 的区别？Agent 是不是"说几句话让 AI 遵守"？

- 都是文本，都属于上下文工程。Rule 是约束（每次加载，或匹配路径时加载）；Skill 是方法（平时只加载描述，用到才读全文，可带脚本）
- Agent 还包括：会用工具的模型本身、真实环境的反馈、代码层面的硬约束（权限、Hook、沙箱）
- 文本规则是软约束；必须 100% 保证的要写成 Hook 或直接不给权限

## 9. 产品、前后端、测试要做成 4 个 Agent 吗？Code Review 是 Agent 还是 Skill？

- 不照搬组织架构。拆 Agent 的依据是：是否需要独立上下文、独立视角、不同权限
- 推荐流程：人写验收标准 → 一个主 Agent 加载不同 Skill 写前后端 → 独立子 Agent 按需求写测试 → 主 Agent 修到测试通过 → CI 自动检查 → 独立子 Agent 审查 → 人审批
- Code Review = Skill（怎么审）+ 子 Agent（独立地审，只读权限）

## 贯穿的主线

1. 模型是概率性的，可靠性来自系统设计
2. 人的角色上移：从"做和查"变成"定标准、做判断、对结果负责"
3. 输入决定输出
4. 偏移来自"自动补全"：让 AI 提问、建立锚点、尽早验证

## 补充：知识库怎么做（RAG vs LLM Wiki）

- 两者目标相同：把对的资料放进上下文。RAG 在提问时理解碎片；LLM Wiki 在录入时就把知识整理好
- LLM Wiki 适合个人或小团队、资料小而精（目录要能放进一个上下文窗口）；RAG 适合资料量大、多人、要分权限、经常更新
- 开源平台（RAGFlow、Dify）解决管道问题，解决不了数据质量问题
- 本仓库的规模，LLM Wiki 单独就够用；加 RAG 主要是为了用熟悉的资料练手
